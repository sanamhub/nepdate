# ADR-0009: What 1.0 promises

- **Status:** accepted
- **Date:** 2026-11-04
- **Approved by:** Sanam

## Context

Ten SDKs shipped release candidates on the 0.x line, and Java, Ruby and Zig are about to make
their first release. The owner decided on 2026-11-04 to skip `0.2.0` final and release
`1.0.0-rc.1` in every port, then `1.0.0`, under the one version line of ADR-0007. Until now the
site said the API could still change before 1.0. A 1.0 line is a promise to the people who build
on it, so the promise has to be written down once, for every port, instead of living in each
port's README.

## Decision

1. **The public API is the surface in `spec/API.md`**, the shared vector behaviour in
   `spec/vectors/`, and the supported range BS 1901-01-01 to 2199-12-30. Everything else is
   internal: modules and types marked internal or private, benchmarks, tools, and error message
   text unless the spec fixes that text.
2. **A breaking change is allowed only in the next major version**, and it lands in every port
   together because ADR-0007 keeps one `MAJOR.MINOR` line for all of them. A deprecation stays
   for at least one minor release before the deprecated surface is removed.
3. **Calendar and patro data updates are not breaking changes** and ship in minor releases. A
   correction that changes an answer for a date is a data update under ADR-0002, not an API
   break, and the changelog says which dates changed.
4. **Between `1.0.0-rc.1` and `1.0.0` only fixes found during the release candidate land.** A new
   feature waits for the next minor, even when the change is small.
5. **A new port joins at the current line.** Before its first release it may declare the line it
   is built for under ADR-0008. At its first release it takes the current line and gets the
   `spec/versions.json` entry that every released port has.

## Consequences

- The site, the READMEs and the release notes can say the API is stable from 1.0 without listing
  each port's exceptions, because there are none.
- A breaking change costs a major release in thirteen repositories on the same day, which is the
  cost ADR-0007 already accepts for a spec change.
- A data fix can ship in a minor without waiting for a major, which keeps calendar corrections
  cheap.
- A port that has not released yet is not held to a line older than the one it ships on, so Java,
  Ruby and Zig can release `1.0.0-rc.1` with the rest.
- The release candidate window is narrow by design: only release-blocking fixes go in after
  `1.0.0-rc.1`.

## Alternatives considered

- **Promise only the functions that have vectors:** smaller, but a user could not rely on the
  documented surface that the vectors do not cover, such as formatting tokens.
- **Let each port decide what 1.0 means:** the ports would drift, and a bug report naming 1.0
  would not say what is guaranteed.
- **Treat data corrections as breaking:** every holiday or tithi fix would need a major release in
  thirteen repositories, which would delay the correction.
